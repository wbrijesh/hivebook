== Context

Several parameters in the system would ideally be computed
dynamically from observed signal — batch frequency from source
heat, sliding-window length from resolution confidence, staleness
tolerance from read traffic and change rate. We do not have the
data to design those functions yet; they require real production
behavior to fit.

Engineering these functions in the design phase produces either
over-cautious or thrashing systems. The pragmatic path is to ship
with constants drawn from configuration, instrument what we need
to derive the functions later, and migrate parameter-by-parameter
once we have data.

This is a deliberate planning posture: we accept that v0.1
behavior is suboptimal in exchange for not over-committing to
guessed dynamic policy.

== Goals

* Ship v0.1 with simple, configurable constants for parameters
that will eventually be dynamic.
* Clearly mark each such parameter and its intended dynamic
trajectory.
* Capture the signals needed to derive the dynamic function once
we have data.
* Avoid premature engineering of dynamic policy.

== Non-goals

* Defining the dynamic functions now.
* Building a generic policy engine. Each parameter graduates
individually when its function is understood.

== Proposal

=== The pattern

Every parameter that follows this pattern lives in the runtime
configuration with:

* A documented constant value (the default).
* A comment or doc entry naming what it would ideally be a
function of.
* Telemetry that captures the signals needed to derive the
function later.

=== Initial parameters under this pattern

The following parameters are tunable defaults in v0.1, with their
intended dynamic trajectory:

[width="100%",cols="29%,15%,56%",options="header",]
|===
|Parameter |v0.1 default |Should eventually depend on
|Batch window (per source) |15 minutes |Source / container heat, artifact arrival rate
|Batch size (per source) |20 artifacts |Average artifact token size, observed LLM call cost
|Recent-resolutions window (N) |10 |Resolution-confidence trend, admin-review frequency per container
|Max stale age before forced rebuild |24 hours |Read traffic on the entry, change frequency in its evidence
|High-confidence filing threshold |0.85 |Observed filing-correction rate over time
|Container-learning trigger |3 confirmations |Admin override rate per container
|===

=== Telemetry requirements

For each parameter, the system records the signals needed to
derive its function later:

* Per container: artifact arrival timestamps, batch fill rates,
resolution-confidence distribution, admin review actions and
outcomes.
* Per entry: read counts, read-after-stale counts, time-to-rebuild,
evidence-change events.
* Per filing: confidence at apply, subsequent corrections by
maintenance or admin.

This telemetry is part of the day-zero data model. It does not
require user-facing surfaces in v0.1 but must be captured.

=== Migration path

A parameter graduates from constant to function when:

[arabic]
. We have at least N weeks of production telemetry for it
(target: 8 weeks).
. A function is fitted offline and reviewed.
. The function ships behind a per-tenant override that falls back
to the constant when uncertain.

Until graduation, the constant is the only behavior. Operators
can override the constant in configuration if a tenant misbehaves;
user admins do not see these parameters.

== Alternatives considered

* *Engineer dynamic functions now.* Speculative; will be wrong;
hard to undo. Rejected.
* *Make every parameter admin-configurable.* Surfaces internal
mechanics to users who shouldn’t need to think about them.
Rejected for v0.1.
* *Hard-code everything with no telemetry.* Cheap now, expensive
later — we’d have no way to graduate parameters. Rejected.

== Tradeoffs

* v0.1 behavior is suboptimal compared to a hand-tuned dynamic
system. Acceptable because we lack the data to do better.
* Each graduation requires effort (fitting {plus} reviewing {plus} shipping).
Acceptable because parameters are few and gains are real.

== Open questions

* Where the configuration lives (per-tenant override mechanism is
undefined).
* Whether some parameters should be tunable per source or per
container even while constants in v0.1.
