== Context

Operational knowledge is about _things_: products, customers,
projects, people, internal tools. The same thing is referenced
differently across sources ("`Acme`" / "`Acme Corp`" / "`Acme Inc`" / a
Salesforce account ID), and within a single source the subject of
a conversation drifts ("`we were talking about Product A; switched
to Product B without explicit naming`").

Without resolving these references to canonical entities, filing
decisions and queries operate on string-level rather than
entity-level truth, which breaks both quality and trust.
Resolution must be mostly implicit and must degrade gracefully to
human-in-the-loop only when the system is genuinely stuck.

== Goals

* Resolve every artifact’s references to canonical entities the
customer cares about.
* Handle within-source subject drift correctly even when batching
splits a conversation across windows.
* Keep admin involvement minimal: an onboarding seed plus
occasional review of genuinely ambiguous cases.
* Allow the system to learn from each admin resolution and reduce
future ambiguity in the same context.

== Non-goals

* Resolving every entity in the world — only those the customer
cares about.
* Maintaining a graph of relationships between entities. Entities
are flat; relationships, if needed later, are a separate
concern.
* Exposing entity resolution as a first-class user surface in
v0.1. Admin uses it through the ambiguity queue and the entity
store view; end users see resolved entities only indirectly
through filing quality and query relevance.

== Proposal

=== Pipeline position

Entity reconciliation runs as a step inside the batched filing
pipeline (xref:ROOT:design-docs/0001-continuous-ingestion-and-filing.adoc[0001]). The same LLM call that files an artifact also
resolves its entities, with the necessary context loaded into the
prompt.

[d2]
----
direction: down
a: Raw ingestion
b: Segmentation
c: Entity extraction + resolution
d: Filing decision + structural changes
a -> b -> c -> d
----

Piggybacking on the filing call rather than running a separate
upstream call means we pay for context once and reuse it.

=== The entity store

A per-tenant store of canonical entities:

[source,yaml]
----
canonical_entity:
  id: <stable-uuid>
  type: person | customer | product | project | internal_tool | other
  canonical_name: "Acme Corp"
  aliases: ["Acme", "Acme Inc", "ACME"]
  source_links:
    - source: salesforce
      external_id: "001..."
      confidence: 0.99
    - source: slack
      external_id: "U03..."
      confidence: 0.85
  admin_curated: bool
  created_at, updated_at

entity_mention:
  id
  artifact_id
  span: <byte or token range>
  canonical_entity_id
  confidence: 0.0–1.0
  resolution_method: explicit | inferred_from_context | container_prior |
                     author_prior | fuzzy_match | admin_resolved
----

=== Sources of entity seeds

In order of strength:

[arabic]
. *Authoritative connectors when present.* CRM populates
customers; HR / SSO populates people; admin-tagged code
repositories populate projects.
. *Onboarding form.* Admin supplies products, services, key
internal tools, major projects. Each with name {plus} 1-line
description {plus} optional aliases.
. *Auto-discovery during ingestion.* Mentioned-but-unmatched
strings cluster across artifacts; clusters above threshold
propose new canonical entities for admin confirmation.

=== Container priors

For each `(source, container)` pair — Slack channel, Drive folder,
GitHub repo, ticket queue — the system records primary-entity
priors:

* Auto-derived when obvious: a channel named `++#++product-foo-design`
with a registered product "`Foo`" auto-tags Foo as the primary
entity with high weight.
* Admin-overridable: admins can pin or remove a container prior.

Container priors feed every batched filing call as context.

=== Recent-resolution sliding window

For each container, the system maintains a sliding window of the
last N artifacts’ resolved entities (v0.1 default: N = 10). This
window travels with the batched filing call to give the LLM
continuity: "`the last 10 messages in this channel were about
Product X`" is a strong prior for the eleventh.

The window length is a *tunable default* (see xref:ROOT:design-docs/0004-tunable-defaults-to-dynamic-functions.adoc[0004]). The
medium-term plan is to compute N dynamically per container as a
function of resolution-confidence trend and admin-review
frequency.

=== Per-batch resolution flow

Within the batched filing LLM call:

[arabic]
. Input context includes:
* Container priors for this container.
* Recent-resolution window for this container.
* Entity store (canonical names {plus} aliases — cheap to send).
* The segmented artifacts in the batch.
. The LLM resolves entities per artifact using, in priority
order:
* Explicit mentions (highest confidence).
* Aliases matching the entity store.
* Inferred context from recent resolutions (handles subject
drift).
* Container priors (lowest weight; used only when other signals
are absent).
. Output per artifact:
* Resolved entities with confidence and method.
* An `ambiguous` flag when no candidate has high confidence,
along with the candidate entities and the reason for
ambiguity.

=== Ambiguity queue

Artifacts with ambiguous resolutions:

* Are still filed (the system does not block ingestion on
ambiguity). Filing uses the LLM’s best guess; entity tags are
marked low-confidence.
* Land in a per-tenant *ambiguity queue* visible to admins or
any user holding the reviewer role.
* Are presented with prior conversation context and candidate
entities for one-click resolution.

To prevent queue overflow at scale:

* *Aggregation.* Similar ambiguities in the same container
during the same window present as one item ("`messages 1–50 in
`++#++channel-foo` 14:00–16:00 — Product X or Product Y?`"). One
click resolves all.
* *Container learning.* When the admin resolves the same
ambiguity the same way 3 times in the same container, the
resolution becomes a soft auto-rule for that container until
contradicted. The threshold (3) is a tunable default (xref:ROOT:design-docs/0004-tunable-defaults-to-dynamic-functions.adoc[0004]).

=== Admin actions on the entity store

* Confirm or reject auto-discovered entity proposals.
* Merge two entities the system created as separate but are the
same thing.
* Split an entity that the system over-merged.
* Add aliases.
* Pin or remove container priors.
* Resolve ambiguity-queue items.

Merges rewrite mentions to the kept canonical ID. Splits trigger
re-resolution of all mentions previously attached to the split
entity (slow; runs in the maintenance loop).

=== Cost characteristics

Resolution piggybacks on the batched filing LLM call — no
additional model calls. Marginal cost is in the input tokens for
context (container priors {plus} sliding window {plus} entity store), all
cheap.

== Alternatives considered

* *Pre-batch dedicated resolution call.* A separate LLM call
upstream of filing. Higher cost without quality gain — the same
context is in scope at filing time.
* *Symbolic resolution only (no LLM).* Fast but fails on
within-document subject drift, coreference, and implicit
context.
* *Full coreference resolution per artifact at ingest.* Expensive
and unnecessary for most artifacts; the batched LLM handles
coreference inline when context demands it.

== Tradeoffs

* Subject drift across batch boundaries depends on the
recent-resolutions window being long enough. Too-short misses
context; too-long inflates LLM input cost. Default 10 is a
guess; will be revised once we have data.
* Admin involvement is unavoidable for the long tail. Aggregation
and container learning are what make it manageable.
* The entity store grows over time. Periodic cleanup of unused or
deprecated entities is a maintenance-loop responsibility.

== Open questions

* Dynamic computation of sliding-window length per container —
deferred per xref:ROOT:design-docs/0004-tunable-defaults-to-dynamic-functions.adoc[0004].
* Schema variants per entity type (a customer has different fields
than a product) — start with one universal schema; specialize
later if needed.
* Cross-customer entity sharing for common public entities
(well-known SaaS products) — out of scope; per-tenant isolation
wins.

== Decisions recorded as ADRs

* Entity reconciliation runs inside the batched filing LLM call, not as
a separate stage — xref:ROOT:adrs/0008-entity-reconciliation-in-filing.adoc[ADR-0008].
* Per-container recent-resolution window length as a tunable default —
xref:ROOT:adrs/0011-constants-first-tunables.adoc[ADR-0011].

The per-container sliding window for subject drift and the
ambiguity-queue mechanism (aggregation + container learning) are
mechanisms internal to this design and remain documented here.
