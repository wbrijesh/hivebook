== 0002 — Mark-and-Defer for Structural Changes

=== Context

The book index is a 3-level DAG: chapter → topic → sub-topic. Every
entry above sub-topic carries a summary that derives from the
entries below it (see the hierarchy invariant in
`architecture/corpus-and-index.md`). When a sub-topic changes —
moved, renamed, summary rebuilt, or its evidence updated — the
summaries of its parent topic and grandparent chapter become
potentially out of date.

Structural changes happen continuously (the batched ingestion
pipeline applies them on every batch — see `0001`) and also
episodically (admin moves). Eagerly rebuilding every dependent
summary on every structural change is unaffordable in LLM cost and
produces unacceptable admin latency. Always-stale derived state is
unacceptable for users.

=== Goals

* Make structural changes (system-driven or admin-driven) fast and
synchronous from the requester’s perspective.
* Keep dependent summaries’ staleness visible to users so they can
reason about what they’re reading.
* Rebuild summaries lazily and in batch to amortize LLM cost.
* Bound the worst-case staleness window.

=== Non-goals

* Real-time consistency of derived summaries with their evidence.
* Blocking admin operations on rebuild completion.
* Cascading invalidation beyond the 3 levels of the book DAG.

=== Proposal

==== The principle

____
*Mark-and-defer.* Every structural change synchronously marks
the directly-affected entries and their ancestors stale in the
index, then returns. Rebuilds happen lazily — on read pressure or
in the maintenance loop, never in the requester’s path.
____

==== What gets marked when

For any structural change to a sub-topic `S`:

[arabic]
. Mark `S.summary` stale (if it has one).
. Mark `S.parent++_++topic.summary` stale.
. Mark `S.parent++_++topic.parent++_++chapter.summary` stale.

For a move that changes parents (sub-topic `S` moves from topic `A`
to topic `B`):

[arabic]
. Mark `S.summary` stale (its context changed).
. Mark `A.summary` and `B.summary` stale.
. Mark `A.chapter.summary` and `B.chapter.summary` stale (only
when distinct).

The walk is O(1) — at most 4 entries marked for any move, 3 for any
other change. Cheap enough to do synchronously in every request.

==== What stale means to a reader

When a user reads a stale summary, the UI surfaces a clear "`summary
being refreshed`" indicator. The stale summary continues to render
because:

* It is usually mostly correct (a typical change affects one
sub-topic out of many).
* An empty page is worse than a marked-stale page.
* The summary’s existing citations still resolve.

==== Rebuild triggers

A stale summary is rebuilt when any of:

* A user explicitly requests a fresh version on the page.
* The first user read of a stale summary in a high-traffic entry
schedules a background rebuild.
* The maintenance loop processes the stale queue.
* The summary’s stale age exceeds `MAX++_++STALE++_++AGE` (tunable default:
24 hours; see `0004`) — forced rebuild on the next maintenance
pass.

==== Rebuild idempotence

Rebuilds are keyed by the content hash of the cited evidence. If
the hash matches the previously built summary’s evidence hash, the
rebuild short-circuits — no LLM call — and clears the stale flag.

This matters because mark-and-defer can mark a summary stale in
situations where the evidence didn’t actually change (e.g., a
sibling sub-topic was renamed). The idempotence check absorbs that
cost.

==== Coalescing and ordering

When multiple structural changes happen in quick succession (e.g.,
a single batch makes 5 structural changes), the resulting set of
stale marks coalesces — the same chapter is not marked stale 5
times; one mark is enough. Rebuilds run only after the marks
settle.

==== Audit

Every mark and every rebuild appears in the audit log with the
correlation ID of the originating change (batch ID or admin
request ID). Operators can trace any summary’s lifecycle from
mark to rebuild.

=== Alternatives considered

* *Eager rebuild.* Rebuild every affected summary synchronously
on every change. Unaffordable in LLM cost; admin operations would
take minutes; cascading rebuilds could thunder under load.
* *No staleness signal.* Pretend everything is current. Bad for
trust; users would not know which summaries to verify.
* *Periodic full-corpus rebuild.* Predictable cost but
catastrophically wasteful — rebuilds entries that haven’t
changed, delays freshness on entries that have.

=== Tradeoffs

* Users sometimes see slightly stale summaries. Mitigated by the
visible indicator and the 24h bounded staleness.
* Cost is concentrated in the maintenance loop, which complicates
capacity planning (it’s bursty). Mitigated by scheduling
maintenance off-peak per tenant region.

=== Open questions

* The right "`high-traffic`" threshold for background rebuild on
read.
* Whether `MAX++_++STALE++_++AGE` should differ by entry level
(chapter vs topic vs sub-topic).
* Long-term: dynamic computation of `MAX++_++STALE++_++AGE` per entry as a
function of read traffic and change rate (see `0004`).

=== Decisions to be recorded as ADRs

* Mark-and-defer as the chosen consistency model for derived
summaries.
* 24h initial `MAX++_++STALE++_++AGE` (subject to the tunable-defaults
pattern).
